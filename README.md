# adb + OpenCV 安卓自动化

用 Python 控制安卓手机：截图 → 识别 → 点击。

## 核心原理

```
adb 截图  →  OpenCV 找图（返回坐标）  →  判断相似度  →  adb 点击  →  循环
```

## 踩过的坑（都是真金白银）

### 环境类

- **Google 源被墙** → 用腾讯镜像 `mirrors.cloud.tencent.com/AndroidSDK/` 下 adb
- **Python 3.14 当时装不上 OpenCV**（2026-09）→ 一度另建 Python 3.12 的 conda 环境。
  后来 OpenCV 5.0.0 出了 3.14 的轮子，现在直接用项目内的 `.venv`（Python 3.14.6）。
- **`cv2.imread` 读不了中文绝对路径** → 用 `os.chdir(ROOT)` 切到项目目录，改用相对路径
- **相对路径找不到文件** → 脚本开头统一 `os.chdir(ROOT)`，在哪运行都对
- **用 bash 的 `>` 重定向存截图会写坏文件**（终端里 `adb ... > x.png`）。
  bash 会把二进制里的 `\n` 换成 `\r\n`，同一张图体积从 20KB 涨到 5.3MB。
  → **截图一律用 Python 的 `open(path, "wb")` 存。**

### 自动化思维类（更重要）

- **命令没报错 ≠ 命令生效了**。adb 的 input 命令失败时经常静默无声。
  → 每次操作后截图对比，验证结果。

- **手机偶尔会丢弃 input 命令**，尤其是刚连接后的头几次。
  → 加预热，不达标就重试。

- **"画面没变"不等于"命令失败"**。列表已经滑到底了也不会变。
  → 校验只能告诉你「有没有变」，判断原因得靠人看截图。

- **`matchTemplate` 永远会返回一个"最像的"结果**，哪怕只有三分像，
  它也绝不说"我没找到"。
  → **必须设相似度阈值**（0.8）。点错地方比什么都不点危险得多。

- **截图前要确保回到了目标界面**。Home 键被丢弃时，截到的是上一个界面，
  后面所有判断全错。
  → 回桌面 → 截图 → 检查分数 → 不够高就重来。

- **一次截图要花 2 秒，但画面是「命令刚开始」那一刻就拍下的**，
  剩下的时间全在压缩和传输。
  → 所以 `sleep` 该等还得等，别指望截图耗时替你等。删掉 `sleep(1.5)` 实测会拍到
  动画中途的画面（与静止桌面差异 68~84，保留 sleep 时是 0.02）。

- **失败可能一声不吭**。`tap 9999 9999`（越界坐标）实测：
  `returncode=0`、`stderr` 全空、**屏幕上什么都没发生**。
  → 只看返回值判断成败是不够的，必须验证**实际结果**。

- **验证指标选错，结论就全错**。用「平均亮度」分不出「动画中途」和「已稳定」
  （119 vs 130 混在噪声里）；换成「与静止桌面逐像素对比」立刻现原形。
  → 挑指标时先问：这个数字**真的**能区分我想区分的两种情况吗？

- **没执行过的代码 = 没写过的代码**。重试分支写完后一直没被跑到过，
  直到把 `THRESHOLD` 设成 2.0（谁都不可能及格）才第一次验证它。
  → 写完分支，必须想办法**逼它执行一次**。

- **设计「失败测试」前，先证明这个输入真的不可能匹配**。
  曾经拿 `template[:50,:50]` 当"假模板"，结果它跟图标原位**一模一样**，
  相似度 1.000 —— 白测一场，还差点冤枉了脚本。

- **`range(1, 3)` 只跑 2 次**，含头不含尾。它不报错，只是默默少做一次。

- **手机 offline 时 `screencap` 一个字节都不吐** → 写出 0 字节的文件 →
  `cv2.imread` 对此**静默返回 `None`**，错误一路拖到几百行外的 `matchTemplate` 才炸，
  报的还是一句跟掉线毫无关系的 `type == _templ.type()`。
  → **截图后立刻检查 `img is None`，在源头报错**；恢复用 `adb reconnect`。

- **匹配数 ≠ 目标数**。同一个图标在屏幕上出现 6 次，`np.where(scores >= 0.8)` 捞出 18 处 ——
  滑动窗口挪 1 像素画面几乎没变，相邻位置分数照样很高（0.848 / 1.000 / 0.848）。
  → 要「最靠上那个」就取 `ys.argmin()`，别把匹配数当成卡片数。

- **能确定的那一步只做一次，别「退到对为止」**。找不到列表时按一次返回是**有把握**的
  （从视频页退一步必然回到列表页）；而「一直退到看见为止」一旦判定出错，
  会一路退出课程、退回桌面。→ 修的时候只做你能确定的那一步。

### Python 语言类

- **`import` 不是"引入文件"，是"把那个文件从头到尾跑一遍"**。
  在 `kit.py` 末尾加一句 `print(...)`，跑 `08_import.py` 时它会**先**喊一嗓子 ——
  你根本没调用它。顺序也说明了：`import kit` 那一行还没执行完，`kit.py` 已经跑完了。
  → 如果那行不是 `print` 而是 `back_home()`，你只是 `import` 了一下，
  **手机就自己跳回桌面了**。所以 `kit.py` 里绝不能有顶层动作。

- **`if __name__ == "__main__":` 就是给上面那条上保险**。
  Python 给每个文件发个名字牌：直接跑是 `"__main__"`，被 import 是文件名的字符串。
  实测：`python lessons/08_import.py` 时测试块一句话不说；
  `python kit.py` 时它照跑。→ 测试代码写在工具文件底部，要用这层保险包起来。

- **`import` 只在「脚本自己所在的文件夹」里找模块**，不是项目根，也不是当前目录。
  `lessons/08_import.py` 找得到 `lessons/kit.py`；`雨课堂/text1.py` 就找不到 ——
  Python 压根没往那个方向看。报错是 `ModuleNotFoundError: No module named 'kit'`。
  → 共用的 `kit.py` 放项目根，子文件夹里的脚本用这 2 行把根目录塞进搜索名单：
  ```python
  sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))
  ```

- **同一个变量被赋了两次，后写的赢，而且一声不吭**。
  给 `kit.load()` 加完"读不到就报错"的防护，**下一行还留着上一版的 `cv2.imread()`** ——
  同一个变量名，防护结果当场被覆盖掉。
  但脚本**照样跑出 `相似度 0.993`**，看着一切正常 ——
  因为 `template.png` 本来就存在，有防护没防护一个样。
  → **加完防护，必须拿一个必然失败的输入试一次**（改成 `images/nothing.png`），
  亲眼看到那句人话打出来，才算验证过。跟当初把 `THRESHOLD` 设成 2.0 逼重试分支执行，
  是同一件事：**跑通了什么都证明不了。**

- **`cv2.imread` 读到不存在的文件不报错，静默返回 `None`**，
  错误会一路拖到 `matchTemplate` 才炸，报的还是那句跟真正原因毫无关系的
  `type == _templ.type()`。之前是**截图失败**踩的，这次是**模板路径写错**踩的 ——
  同一个坑，两个入口。→ 凡是 `imread` 读出来的东西，第一件事就是查 `None`，
  并且把**是哪个文件**报出来（`kit.load` 干的就是这个）。

### 出错处理类

- **`exit()` 不是在"停止程序"，它是扔出一个叫 `SystemExit` 的异常**。
  实测：`try: kit.load("不存在的图") except BaseException as e: print(type(e).__name__)`
  打出来的就是 `SystemExit`，而且程序**活下来了**。
  → 它只是被扔出去、没人接、一路飞出整个文件才把程序带走的。**能被接住，就说明它不是圣旨。**

- **工具函数不该用 `exit()`**。`kit.py` 里一个装工具的模块，凭什么替**调用者**决定
  "整个程序去死"？而且 `exit()` 一触发，调用者**连伸手接的机会都没有** ——
  想实现"掉线自动重连"，用 `exit()` 根本写不出来。
  → 工具函数只管 `raise` 说清出了什么事，**怎么处理交给调用者**。

- **重试之前必须先改变条件，否则只是把同一个失败重播一遍**。
  手机 offline 时你光 `sleep` 再试一次，收效为零 —— 得先 `adb reconnect` 把它拉回来。
  跟"预热"那条是同一个道理。

- **重试只能对付「偶发抖动」，对付不了「真断线」**。真拔线实测：
  `reconnect` 连试 5 次也救不回来（线都拔了，reconnect 能救什么）。
  → 重试的价值在"抖一下自己就好了"这个场景，别指望它扛住物理断连。

- **`adb kill-server` 模拟不了掉线**。本以为干掉服务就能造出 screenshot 失败，
  实测 adb 客户端**自动把 daemon 拉起来了**，照样截到 20238 字节。
  → 想造"偶发失败"，只有在代码里造假（把 `shot` 换成一个按你的剧本失败的假函数），
  这跟当初把 `THRESHOLD` 设成 2.0 逼重试分支执行是同一个套路：
  **让失败听你的话，那个分支你才一定跑得到。**

- **Windows 控制台是 GBK 编码，emoji 打不出来**。
  `print(f"❌ {e}")` 实测直接 `UnicodeEncodeError: 'gbk' codec can't encode character '❌'`。
  中文没事（GBK 里有），emoji 没有。
  → **而且它崩的位置最要命：崩在 `except` 块里 —— 错误处理代码自己出错了**，
  后面那句"决定权在我手上"根本没轮到打印。

## 三条铁律

1. **验证** —— 每步操作后检查结果，别假设成功
2. **重试** —— 单次失败很正常，给 2~3 次机会
3. **达标才动手** —— 分数不够就不点，宁可卡住也不乱点
